# 🤖 Инструкция для ИИ-агента: система обучения управленческим навыкам

> Этот файл — самодостаточная инструкция для агента (hermes_a / hermes_b),
> работающего с репозиторием. Мастер-промпт системы — в `MASTER_PROMPT.md`
> (копия в ~/wiki). Следуй жёстким границам приватности ниже.

## 1. Что это за репозиторий

**Personal OS Learning** — система ежедневного обучения управленческим навыкам
для госслужбы. Публикуется на GitHub Pages (существующий Kosetor/personal-os,
текущий план, без приватных Pages).

> ⚠️ Репозиторий ПУБЛИЧНЫЙ. В него попадает только обезличенная статика.
> Вся приватная информация — строго в `~/personal-os-private/` (ВНЕ git).

## 2. Структура

```
personal-os/                 ← этот git-репозиторий (публикуется)
  site/                      ← публикуемая статика (Pages деплоит эту папку)
    index.html               ← «сегодня»: статья дня + тест
    articles/                ← архив статей (HTML)
    assets/audio/            ← подкасты .mp3
    data/                    ← knowledge-graph.json, progress-public.json
    progress/                ← граф тем (D3) + сводка
  content/published/         ← утверждённые исходники статей (markdown)
  content/drafts/            ← черновики (НЕ публикуются)
  .github/workflows/deploy-pages.yml

~/personal-os-private/       ← ВНЕ git, только локально
  learning.db                ← SQLite: темы, статьи, попытки, FSRS, напоминания
  logs/
  sources-private/           ← нормативка, законы, СНиП (для фактчекинга)
    laws/ standards/ articles/
```

## 3. ЖЁСТКИЕ ГРАНИЦЫ ПРИВАТНОСТИ (никогда не нарушать)

В git/Pages НЕ попадает:
- `learning.db`, история ответов, детали прохождения тестов;
- исходные PDF/тексты нормативов, локальная RAG/векторная база;
- логи, токены, ключи, Tailscale-конфиг, Telegram-ID;
- черновики `needs_manual_review`;
- внутренние промпты и заметки со служебной информацией.

В Pages можно только:
- утверждённые статьи (HTML/MD) и сгенерированные аудио;
- инфографику;
- `progress-public.json` (статусы тем, даты повторений, агрегированные % — БЕЗ
  пошагового лога ответов);
- данные графа тем (узлы, рёбра, статус — без чувствительных деталей).

Сомневаешься — не публикуй: пометь `needs_manual_review`, спроси владельца.

## 4. Основной ежедневный цикл (cron)

- **08:00** — публикация статьи дня: тема → черновик → фактчекинг нормативов →
  подкаст (TTS) → инфографика → HTML с аудио и кнопкой «Я изучил материал» →
  обновить `site/index.html` → push.
- **20:00** — проверка активности: статья прочитана? тест пройден? → напоминания
  в Telegram. 3 дня без активности → «возвратный» сценарий.
- После каждого теста — обновить FSRS в `learning.db`, пересчитать статусы тем,
  сформировать `knowledge-graph.json` + `progress-public.json`.

## 5. Фактчекинг нормативов (обязательно)

Любой закон/СНиП/норма в статье:
1. Найти точную формулировку в `~/personal-os-private/sources-private/`.
2. Вставить ссылку на статью/пункт + дату проверки в `source_registry`.
3. Нет подтверждения → статус `needs_manual_review`, публикация блокируется,
   владельцу — уведомление, что именно проверить.

**Никогда не придумывай ссылку на норматив.** Приоритет источников:
научные публикации → официальные источники → проверенные учебные пособия →
свежие публикации.

## 6. Модель компетенций (учебный план)

8 блоков → 20-30 тем-узлов с рёбрами-предпосылками:
1. Стратегическое мышление
2. Командное взаимодействие
3. Персональная эффективность
4. Гибкость и готовность к изменениям
5. Принятие управленческих решений
6. Лидерство
7. Административные и нормативно-правовые компетенции
8. Информационно-коммуникативные компетенции

Полная схема и FSRS-алгоритм — в `MASTER_PROMPT.md`.

## 6.1. Фактические границы этой версии сайта

- В репозитории есть статические статьи, аудио, граф и публичный снимок прогресса.
  Здесь нет приватной БД, исполняемого планировщика, FSRS или веб-интерфейса тестов.
- Кнопка «Прочитано» — отменяемая отметка для конкретной статьи в браузере.
  Она не отправляется hermes_a и не доказывает прохождение теста.
- Число опубликованных статей не равно числу изученных тем. Главная читает
  прогресс из `site/data/progress-public.json`; не подменяй его числом публикаций.
- `MASTER_PROMPT.md` отсутствует в этом репозитории. Получи его на устройстве
  владельца; не сочиняй алгоритм FSRS, задания cron или схему БД по упоминаниям.
- Активный исполнитель сейчас — hermes_a. Не ожидай подтверждения или обработки
  от недоступного hermes_b. Подтверждение владельца и фактчекинг остаются обязательными
  там, где они требуются для материалов.

## 6.2. Восстановление остановившегося процесса (hermes_a)

На устройстве с приватной системой:

1. Установи фактические пути БД, исходников и генератора, команды планировщика,
   выбранный IANA-часовой пояс и последние успешные запуски. Время 08:00/20:00
   применяется в этом явно заданном часовом поясе, а не по UTC или часовому поясу
   случайного компьютера. Сделай локальную резервную копию БД перед изменениями.
2. Сверь утверждённые статьи в приватной системе с `site/articles/` и архивом:
   для каждой статьи HTML, MP3, SVG, дата публикации и стабильный идентификатор темы.
   Составь список пропусков. Не генерируй и не публикуй автоматически задним числом
   «недостающие дни» и не считай отсутствие статьи доказательством непрохождения теста.
3. Проверь реальные попытки и оценки тестов в БД и фактически настроенный канал
   тестирования. Различай: опубликовано / прочитано / тест выдан / ответ получен /
   оценён / FSRS обновлён / снимок выгружен. Не выставляй успех без ответа пользователя.
   Не повышай статусы тем по кликам, публикации или датам файлов.
4. Найди первый незавершённый шаг и его ошибку. Исправь причину и повтори только
   этот шаг. Используй блокировку от параллельного запуска и идемпотентность по ID
   статьи/попытки: повторный запуск не должен дублировать публикацию, оценку или FSRS.
   Отмечай отсутствие доступа как блокировку, а не как успешное выполнение.
5. Выгружай `knowledge-graph.json` и `progress-public.json` из одного состояния БД
   с одинаковой датой `updated`. Проверяй суммы статусов, IDs тем, связи и даты
   повторений. Не меняй `updated` только ради скрытия устаревания. Не добавляй
   персональные ответы или логи в публичные файлы.
6. Проверь утреннюю публикацию и вечернюю проверку фактическими запусками на
   приватном устройстве. GitHub Pages только развёртывает готовый сайт после push;
   зелёный деплой не подтверждает работу расписания обучения.
7. После восстановления сверяй последнюю ожидаемую публикацию и экспорт с
   расписанием. Если шаг пропущен, оставь в приватном журнале этап, ошибку,
   следующий шаг и время повторной попытки. Сообщай владельцу только о новом
   сбое, необходимом действии или восстановлении, без повторного спама.

## 6.3. Проверка перед публикацией

- Запусти `python scripts/check_site.py` и `node --test tests/*.test.cjs`.
  Предупреждение об устаревшем снимке требует сверки с приватной системой,
  а не ручного увеличения счётчиков. Эти проверки не оценивают ответы пользователя.
- Проверяй закон/пункт и источник по разделу 5. Отсутствие ошибки в HTML-проверке
  не означает, что факты проверены. Реестр источников и утверждённые исходники
  должны существовать в фактическом процессе; не приписывай им проверку без доступа.
- Рендери Markdown-заголовки всех уровней. Не допускай видимых `####` в HTML.
  При изменении генератора перенеси исправления чтения, прогресса и шаблонов в него,
  чтобы следующая статья не восстановила старое поведение.
- Открой главную, статью и прогресс на широком и мобильном экране. Проверь
  ссылки, загрузку аудио, инфографику, чтение двух разных статей, перезагрузку
  и отмену отметки. Не проходи учебные тесты от имени владельца ради проверки UI.
- После push дождись успешного деплоя именно отправленного commit SHA и проверь
  опубликованные URLs. При сбое сохрани причину в приватном журнале и исправь
  или откати конкретное изменение. Не объявляй материал опубликованным до проверки.
