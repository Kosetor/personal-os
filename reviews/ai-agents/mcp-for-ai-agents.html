Суть материала

MCP (Model Context Protocol) — открытый стандарт подключения ИИ-приложений к внешним системам: данным (файлы, базы данных), инструментам (поиск, калькуляторы) и воркфлоу (специализированные промпты). Официальная документация называет его «USB-C портом для ИИ-приложений»: как USB-C унифицировал подключение устройств, так MCP унифицирует подключение агентов к внешнему миру. Протокол представлен в конце 2024 года и активно развивается открыто — текущая версия спецификации датирована 2026-07-28.

Архитектура клиент-серверная, в ней три участника. MCP Host — ИИ-приложение (например, Claude Desktop, VS Code или Hermes), которое инициирует соединения. MCP Client — компонент внутри хоста: на каждый сервер создаётся свой клиент с выделенным соединением. MCP Server — программа, которая предоставляет контекст и возможности; она может работать локально (транспорт stdio: JSON-RPC по стандартным потокам запущенного подпроцесса) или удалённо (транспорт Streamable HTTP: POST на единый endpoint, ответ JSON или SSE-потоком). Протокол основан на JSON-RPC 2.0 и вдохновлён Language Server Protocol.

Три участника MCP: хост управляет клиентами, каждый клиент держит выделенное соединение со своим сервером, сервер отдаёт инструменты, ресурсы и промпты.

Серверы предлагают три примитива. Tools — функции, которые модель вызывает сама (обнаружение через tools/list, исполнение через tools/call, схемы на JSON Schema); это «действия»: запись в БД, отправка сообщений, вызов API. Resources — пассивные read-only данные для контекста (URI + MIME-тип). Prompts — готовые шаблоны инструкций и воркфлоу, которыми управляет пользователь. Со стороны клиента доступны elicitation (сервер запрашивает данные у пользователя) и sampling (сервер запрашивает LLM-вызовы через клиента); в версии 2026-07-28 sampling и roots помечены deprecated. Спецификация написана в терминах MUST/SHOULD (RFC 2119), а безопасность — её неотъемлемая часть: человеческий контроль, согласие пользователя, минимальные привилегии и песочницы описаны как требования, а не как советы.

Почему это важно

  • Стандартизация вместо N интеграций. Без MCP каждый агент интегрируется с каждым сервисом отдельно — квадратичный рост кода. С MCP достаточно один раз реализовать клиент, и он получает доступ к целой экосистеме серверов: от референсных (filesystem, GitHub, базы данных) до серверов от Anthropic, OpenAI и сообщества. Поддержку протокола имеют Claude, ChatGPT, VS Code, Cursor и десятки других инструментов.
  • Разделение ответственности. Сервер инкапсулирует доступ к данным и права (кому и что открыто), хост отвечает за UX и политики безопасности, а модель — за выбор инструментов. Каждая сторона контролирует свою часть, что упрощает аудит и изоляцию.
  • Безопасность заложена в протокол. Спецификация и руководство по безопасности описывают атаки и контрмеры: «confused deputy», SSRF, перехват токенов, компрометацию локальных серверов. Принципы — least privilege, сужение scope токенов, human-in-the-loop для инструментов — зафиксированы как требования к реализации.
  • Открытость и экосистема. Спецификация, SDK, референсные серверы и MCP Registry живут в открытых репозиториях; развитие идёт через публичные предложения (SEP). Для персональной автоматизации это означает: протокол не привязан к одному вендору и не исчезнет вместе с ним.

Практическое применение

Сценарии, которые описывает документация MCP и которые напрямую реализуются поверх протокола:

  • Локальные серверы через stdio (npx, uvx или любой исполняемый файл): доступ к файловой системе, GitHub, базам данных — сервер запускается как подпроцесс, обмен идёт по stdin/stdout.
  • Удалённые серверы через Streamable HTTP с авторизацией (OAuth 2.1 для серверов, заголовки для частных endpoint'ов) — для облачных и корпоративных сервисов.
  • Модель сама находит и вызывает инструменты: tools/list для обнаружения, tools/call для исполнения. Интеграцию не нужно хардкодить — она описывается схемами инструментов.
  • Типовые кейсы из документации: агент, работающий с Google Calendar и Notion; IDE, генерирующая приложение по макету Figma; чат-бот предприятия, анализирующий данные из нескольких баз.
  • Инструменты разработчика: MCP Inspector для отладки серверов, клиентские best practices для масштабирования хоста на много серверов и инструментов.

Ограничения и риски

  • Документировано источником: инструменты — это произвольный код. Компрометация локального сервера означает произвольное выполнение команд с правами клиента, эксфильтрацию данных и их потерю; поэтому требуются sandboxing/контейнеры и явное согласие пользователя.
  • Документировано источником: «не доверяй по умолчанию» — ни серверу, ни клиенту. Официально описаны атаки на прокси-серверы («confused deputy»), подмена авторизации (SSRF), проброс токенов и перехват состояния. Секреты и ключи не должны попадать в промпт/контекст модели.
  • Документировано источником: scope minimization — токен с широкими правами (files:*, admin:*) усиливает ущерб от любой утечки; запрашивать нужно только необходимые scope. Для необратимых действий спецификация требует human-in-the-loop с возможностью отклонить вызов.
  • Документировано источником: протокол быстро меняется: в версии 2026-07-28 sampling и roots объявлены deprecated, появляются расширения (Tasks, Skills over MCP, MCP Apps) — реализации нужно обновлять и перепроверять.
  • Практическая интерпретация: MCP решает проблему интеграции, но не проблему доверия: качество и безопасность серверов различаются, поэтому подключать стоит проверенные серверы, а каждому давать минимум прав и таймауты.

Что можно сделать в Personal OS / Hermes

Этот раздел — практическая интерпретация для Personal OS на основе документации Hermes Agent (нативный MCP-клиент), а не пересказ спецификации MCP.

  1. Установить зависимость: Python-пакет mcp (pip install mcp) — без него нативный MCP-клиент Hermes молча отключается. Для npx-серверов нужен Node.js, для uvx-серверов — uv.
  2. Прописать серверы в конфиге ~/.hermes/config.yaml в ключе mcp_servers: stdio-сервер задаётся command/args, удалённый — url/headers (или command, или url — не оба). Для каждого сервера настраиваются timeout и connect_timeout.
  3. Перезапустить Hermes: при старте discover_mcp_tools() подключается к серверам, вызывает tools/list и регистрирует инструменты с префиксом mcp_<сервер>_<инструмент> (дефисы и точки заменяются на подчёркивания). Инструменты автоматически внедряются во все платформы — CLI, Discord, Telegram.
  4. Секреты — только явно: stdio-подпроцессам передаётся отфильтрованное окружение (PATH, HOME, USER, LANG, LC_ALL, TERM, SHELL, TMPDIR, XDG_*), все остальные переменные (ключи API, токены) отсекаются, если не указаны вручную в env сервера. Credential-паттерны в сообщениях об ошибках автоматически редактируются — секреты не утекают в подпроцессы и в контекст.
  5. Ограничить sampling: серверы могут запрашивать LLM-вызовы (включено по умолчанию) — задать max_tokens_cap, max_rpm, allowed_models, max_tool_rounds против бесконечных циклов, а для недоверенных серверов — sampling: { enabled: false }.
  6. Минимальные права и человеческий контроль: подключать только нужные серверы с минимальными привилегиями; для деструктивных команд держать approval-режим (approvals.mode: smart/manual) — практический аналог human-in-the-loop из спецификации.
